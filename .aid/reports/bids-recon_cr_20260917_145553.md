  <design_principle>
    Code encodes physics and standards; config encodes protocol and convention. Physics-based checks (_is_epi, _is_spin_echo ScanningSequence branch, Rule 4 inversion-time/scanning-sequence logic, bval checks) derive from how MRI acquisition works and belong in code. Convention-based checks (keywords, token names, expected counts, enforcement policy) depend on how vendors/sites/protocols name and organize things. These vary across deployments and must be parameterized through configuration.

      <recommendation>
        Replace all hardcoded convention-dependent assumptions with 7 config fields. T1W/T2W automated demotion requires a two-key gate (expected_anat_count exceeded AND calibration keyword match) to prevent false demotions. Cross-invocation registry enforcement requires independent controls for volume counts, label freezing, and rename detection (F4). Specific config fields and exhaustive defaults below.

        1. scout_keywords (list of strings)
           Default: ["scout", "localizer", "survey", "3-plane", "3plane", "aascout", "aahscout", "locator", "scanogram", "plan scan", "planscan", "topogram"]
           Replaces: _SCOUT_KEYWORDS (line 188). Code reads from config instead of frozenset.

        2. calibration_keywords (list of strings)
           Default: ["setter", "prescan", "_cal_", "calibration", "coilsurv"]
           Replaces: _CALIBRATION_KEYWORDS (line 189). Code reads from config instead of frozenset.
           Note: R3 confirmed calibration naming is site-specific. Users should augment this list for their protocols.

        3. norm_tokens (list of strings)
           Default: ["NORM", "PURE", "SCIC", "CLEAR"]
           Replaces: hardcoded "NORM" checks in NORM/ND pass (lines 428, 444, 464, 476-477).
           _has_norm_token(s, config.norm_tokens) checks both image_type_text and image_type against the configurable set.
           Note: PURE/SCIC (GE) and CLEAR (Philips) are unverified for DICOM field presence but safe to include (no false positives if absent from fields). DIS2D/DIS3D/ND excluded: these are distortion-correction flags, not intensity-normalization indicators, and serve different purposes in the pipeline.

        4. expected_anat_count (dict or null)
           Default: null (no expectation, no auto-demotion)
           Example: {T1W: 1, T2W: 1}
           New field. When set, enables count-based anomaly detection after NORM/ND pass:
           - Count exceeds expectation AND series matches calibration_keywords AND description_stem differs from non-keyword series of same type: demote to DROP_CALIBRATION.
           - Count exceeds expectation AND no keyword match: DUPLICATE_MODALITY warning at HIGH severity (no auto-demotion).
           - Count at or below expectation: no action regardless of keywords.
           - Null (not configured): DUPLICATE_MODALITY warning only (current behavior).

        5. registry_mode (string: "advisory" or "strict")
           Default: "advisory"
           Replaces: hardcoded strict enforcement in check_volume_counts (runs.py:101-114).
           "advisory": registry mismatch produces HIGH-severity warning; within-session reasoning remains enforcement.
           "strict": current behavior (registry mismatch excludes series).

        6. label_freeze_mode (string: "frozen" or "re-derive")
           Default: "frozen"
           Controls label resolution behavior in resolve_labels (labels.py:295-312). See F4 for full rationale.
           "frozen" (default): current behavior. Registered labels are reused verbatim; drift guard is active and halts on mismatch.
           "re-derive": labels are re-derived fresh each invocation using the current session's prefix. Registry labels are used only for consistency logging (warn if the re-derived label differs from the registered label). Drift guard produces a warning instead of a halt.

        7. rename_detection (string: "strict" or "warn" or "off")
           Default: "warn"
           Controls rename detection behavior in resolve_labels (labels.py:330-365). See F4 for full rationale.
           "strict": current behavior. Label or signature collision with an absent registry description triggers TaskRenameError (pipeline halt).
           "warn" (default): collision produces a HIGH-severity warning instead of a halt. Processing continues with the auto-derived label.
           "off": rename detection is skipped entirely. Appropriate for datasets with known protocol evolution across participants.
      </recommendation>

      <description>The task registry's cross-invocation enforcement assumes protocol stability: that SeriesDescriptions, their derived labels, and their acquisition signatures remain constant across pipeline invocations. This assumption breaks in heterogeneous datasets where different scanners use different naming conventions for the same task, protocols evolve mid-study (tasks added or dropped for later participants), or participants return on different days with different session compositions. Two mechanisms produce false halts: (1) The rename detection guard (labels.py:330-365) compares new descriptions against old registry descriptions absent from the current session. When a protocol change legitimately drops a task and adds a new one whose auto-derived label collides with the dropped task's registered label, TaskRenameError fires incorrectly. Similarly, when different scanners produce different SeriesDescriptions for the same task that derive to the same label, the guard interprets this as an undeclared rename. (2) The label drift guard (labels.py:295-312) freezes the label-derivation prefix from the first invocation. When session composition changes (different scanner, different task set), the common prefix changes, and the frozen label no longer matches fresh derivation, triggering LabelDriftError.</description>
      <evidence>
        Code inspection of labels.py:330-365 (TaskRenameError): old_registry_descs (line 283) collects descriptions present in the registry but absent from the current session. Lines 337-363 check whether any new description's auto-derived label or acquisition signature matches an old registry description's label or signature. This comparison is unconditional: there is no mechanism to suppress it for known protocol changes.
        Code inspection of labels.py:295-312 (frozen label + drift guard): stored_prefix (line 300) is loaded from the registry entry written by the first invocation that registered the description. If the current session's common prefix differs (because the set of descriptions changed), the drift guard detects the mismatch and halts.
        Cross-invocation state flow confirmed via pipeline.py:347-351 (Phase 4 registry save persists merged_registry to YAML) and config.py:349-376 (registry loaded from YAML at config parse time).
      </evidence>
      <literature>N/A (code analysis only; no external research required).</literature>
      <impact>In a multi-scanner or protocol-evolving dataset: (1) Rename detection false halts block processing of later participants whose scanner or protocol version produces different SeriesDescriptions that collide in label-space with discontinued or differently-named tasks from earlier participants. (2) Label drift false halts block processing when a participant's session composition (different scanner, subset of tasks, added tasks) changes the common prefix relative to the invocation that first registered the description. Both failures require manual intervention (registry editing or clearing) to resolve, undermining the pipeline's goal of automated, unattended processing.</impact>
      <recommendation>
        Add label_freeze_mode and rename_detection to the config schema (F1 fields 6-7).

        label_freeze_mode (F1 field 6): "frozen" (default) preserves current behavior for stable-protocol sites. "re-derive" re-derives labels fresh each invocation, using the registry only for consistency warnings, not enforcement. This eliminates the LabelDriftError false-halt pathway in heterogeneous datasets while preserving the warning signal for sites that want to monitor label stability.

        rename_detection (F1 field 7): "warn" (default) downgrades TaskRenameError to a HIGH-severity warning, matching the advisory philosophy of registry_mode's default. "strict" preserves current behavior. "off" skips rename detection entirely for datasets with known protocol evolution.

        The three registry enforcement fields (registry_mode, label_freeze_mode, rename_detection) form a coherent policy surface: each independently controls one cross-invocation enforcement mechanism, and the defaults collectively favor warnings over halts, matching the design principle that cross-participant state should inform but not block per-participant processing.
      </recommendation>
